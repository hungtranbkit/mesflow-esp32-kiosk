# ESP32-S3 kiosk scheduled deep sleep — bench prototype

Schedule is **disabled by default** until actual timed wake and headless USB recovery are proven. `kiosk-sleep on 22:00 06:00` stores a complete schedule record in NVS; `kiosk-sleep off` is the persistent maintenance override. USB `kiosk-sleep test 15` requests a bounded 15-second test and allows durable queued telemetry only; all other busy conditions still block it. Scheduled sleep retains the telemetry guard. All commands require a functioning USB console. After boot there is a two-minute grace window before scheduled sleep. Clock before 2024 fails awake; unsynchronized but plausible wrong clock cannot be detected solely by the epoch. Schedule is recomputed in Vietnam local time from the current synchronized clock whenever the kiosk is awake. A clock change during deep sleep cannot be observed until timer wake.

The application refuses sleep if there is a pending transaction or offline event, an action event awaiting delivery, active worker/operation/session, partial scanner frame, OTA activity/claim, setup, maintenance, enrollment, calibration, diagnostic or recovery mode, or a non-READY screen. Scheduled sleep also defers for recent input. The OTA worker and sleep entry use an exclusive cross-core gate; other asynchronous activity and hardware recovery still require validation before production. S3 deep sleep turns off backlight GPIO45, sets timer wake, and executes `esp_deep_sleep_start`; boot restores display and reconnects network. ESP deep sleep can make USB CDC unavailable until a timer wake or external reset. The GM65 power supply is not switched by this firmware.

Test evidence must include a confirmed timer wake and separately demonstrate remote ROM USB recovery during sleep before enabling the overnight schedule on a headless device. `KioskTimerWakes` persists a counter of timer wake causes so a later USB reset does not erase evidence. Backups contain secrets and must remain private. Do not claim measured power consumption, physical scanner sleep, 06:00 wake, or MESFlow binding without actual observation. No production fleet rollout is authorized by this bench prototype.

## M910 39:84 bench — 2026-11-24

App-only build SHA256 `327120315f0771733608602e938f3797b33904f73cfc68100d7f7be06fc22f88` was verified on board 84:C7:BB:79:39:84; its build identity references the dirty base f44d851 and is a bench artifact. Full flash backup was captured and verified before testing; NVS/otadata verified after each app-only write. First test refused with 12 durable telemetry events. The bounded test command was then limited to permit queued telemetry while retaining all transaction/OTA/enrollment/diagnostic guards; scheduled operation still blocks on that queue. Two 15-second tests produced two persisted timer wake counts; kernel logged a 15-second USB disconnect/re-enumeration. After wake USB ROM flash-id worked, and boot/status showed WiFi connected, keypad calibrated, scanner UART 9600, MESFlow unbound and schedule OFF.

**Critical hold:** during the second deep sleep, the USB device disappeared and `esptool --before no-reset` could not open the port (ENOENT); it reappeared only on timer wake. This does not demonstrate out-of-band USB recovery during a long sleep. Do not enable the overnight schedule on this headless board until an independently controlled reset/boot or other recovery path is installed and verified. Actual 06:00 wake, direct LCD visibility, scanner power, and electricity use have not been measured. GM65 power remains unchanged.

## OTA interlock update — 2026-11-24

The OTA worker reserves an OTA lease under a cross-core critical section before task creation and releases it only after the check/update routine has returned. Sleep reserves the mutually exclusive sleep lease under the same lock before enabling its timer; failure paths release it. This closes the race between starting the OTA worker and entering sleep. Host interleaving tests cover both acquisition orders, failure cleanup and 1,000 concurrent attempts; an actual live OTA versus sleep race remains untested. `kiosk-sleep test 30` is a bounded USB-only 30-second test; the scheduled feature remains disabled by default and must remain off until out-of-band recovery during deep sleep has been demonstrated.

## OTA gate and 30-second trials — 2026-11-24

Board 84:C7:BB:79:39:84 was running app SHA256 `327120315f0771733608602e938f3797b33904f73cfc68100d7f7be06fc22f88`; the exact app and a fresh full flash backup were verified against chip. The OTA gate test build app SHA256 `ef2e649de6b2cb13e33621c061d0c326a0b77a441d20dc95ce8261b7d5b84d03` was app-only flashed at 0x10000 and verified; NVS/otadata matched the preflash snapshot.

With schedule OFF, two bounded `kiosk-sleep test 30` trials re-enumerated the same USB device after 30.377 s and 30.335 s. The NVS timer wake counter, incremented only for `ESP_SLEEP_WAKEUP_TIMER`, advanced 2→3→4. Each post-wake boot initialized display and keypad, brought up scanner UART 9600 and reconnected Wi-Fi; MESFlow remained unbound. The command `kiosk-sleep off` returned DISABLED and status after USB reset read OFF. Screen pixels, real keypresses, scanner data and power consumption were not physically verified.

During sleep the USB by-id disappeared and esptool could not open it (exit 2); only timer wake restored access. Therefore remote recovery before the timer is **not verified**, and automatic overnight sleep remains OFF. Before enabling, install and test an independent remote reset/boot path and validate runtime interactions with OTA. The OTA/sleep gate passed 1,000 host-thread races but an actual OTA-vs-sleep concurrency test was not run on hardware. Build metadata names the dirty source parent; use the recorded binary SHA and source tree, not the build ID alone, to identify this bench image.
